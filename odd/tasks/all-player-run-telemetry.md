# All-Player Run Telemetry

Objective: Automatically record gameplay-run telemetry without a username or player ID, expose aggregate run metrics, and keep delivery non-blocking. Branch: `feature/architecture-review-deepening`. Delivery: `stacked-to-main` (forecast ~650 authored changed lines). Runner: `node --test tests/*.test.mjs`.

## Specs

- S1 — User request: “No quiero que borrer sus propios registros, quiero que unicamente se guarden los datos de las corridas en el juego bien sea con un username escrito o generado por el sistema, lo que queria era monitoreas las cantidades de veces que ha sido jugado el jeugo, cuando a durado una persona, las veces que sobrevivio o murio, todo a modo de observabilidad”. Later clarification: “si me sirve”. Acceptance: record run starts and terminal summaries automatically, without requiring approval, a username, or a user ID; expose aggregate play counts, durations, and outcomes. Keep the game playable when Supabase is unavailable.
- S2 — User request: “quiero que sea automatico sin aprobacion del usuario”. Acceptance: telemetry is enabled by default with no affirmative-approval checkbox and a clear visible notice. Preserve the previously selected persistent opt-out unless the user changes that choice. Do not publish a username or per-player leaderboard.
- S3 — User accepted the proposed aggregate-only privacy model with “si me sirve”: no username or user ID in telemetry or the durable browser queue; no IP, user-agent, email, location, device-fingerprint, or mental-health fields in game-owned tables/application logs; disclose provider-side connection-metadata processing. Do not create anonymous Auth users for telemetry. Do not expose individual run rows or provide a player-facing delete path. A per-run UUID may be used only to deduplicate delivery for that run; it must not link runs to a person. Do not add a service-role key to browser code.
- S4 — Reliable delivery: queue run data durably in the browser before network submission; replay on eligible startup/online/visibility events; use a stable per-run idempotency key; clear pending data only after server confirmation or explicit telemetry opt-out. A terminal retry must ensure its `in_progress` start is recorded first; the RPC rejects terminal-only inserts. Exact duplicate terminal payloads are harmless; conflicting terminal payloads are rejected. No Auth identity or user ownership is involved. If IndexedDB is unavailable, best-effort direct writes may run only when the start row is confirmed; never insert a terminal-only run. Expose only aggregate results; deny direct row reads, updates, and deletes to browser roles. Acceptance: tests prove retry, replay, duplicate safety, opt-out queue removal, no user identifier/auth call, no delete capability, and non-blocking gameplay. Do not contact or modify a live Supabase project in this task.
- Assumption: capture only the existing run summary and lifecycle (`in_progress`, `rescued`, `jumped`); do not add new behavioral, device, or identity fields. Preserve historical database rows; this change does not authorize deleting or rewriting existing production data.
